# Collateral AI backend — Django + DRF guidelines

Source of truth for how code is structured here. Applies to humans and AI agents. Generated by
**cookiecutter-django** (`rest_api=DRF`); keep to its layout and the rules below.

## Golden rules (read first)

1. **Views stay empty.** Put all logic in **serializers** (validation/shaping) and **service
   classes/functions** (business operations). A view should only wire a serializer + queryset +
   permissions together.
2. **Use the highest-level DRF class that fits.** Prefer `ModelViewSet` > `ReadOnlyModelViewSet` >
   mixins + `GenericViewSet` > `APIView` > `@api_view`. Do **not** hand-write a custom view unless a
   generic genuinely cannot express it. Justify any drop down the ladder in a comment.
3. **Use the highest-level model/base class** and inherit shared behavior. Put common fields/behavior
   on an abstract base model (e.g. `TimeStampedModel`) and inherit it everywhere; don't repeat
   `created`/`modified`/uuid logic per model.
4. **Fat models are fine for intrinsic behavior; cross-model workflows go in services.**

## Layout

```
backend/
├── config/
│   ├── settings/{base,local,production,test}.py
│   ├── api_router.py       # register EVERY ViewSet here (versioned)
│   └── urls.py             # admin, /api/, /api/schema/, /api/docs/, /health/
├── collateral_ai/
│   ├── core/models.py      # abstract bases: TimeStampedModel, UUIDModel, ...
│   ├── users/
│   └── <app>/
│       ├── models.py
│       ├── api/
│       │   ├── serializers.py
│       │   └── views.py    # ViewSets only — thin
│       ├── services.py     # business logic (transactions, workflows)
│       ├── selectors.py    # non-trivial read queries (optional)
│       └── tests/
└── pyproject.toml          # deps via uv (uv add / uv sync) — NOT requirements.txt
```

## URL & routing conventions

- **All API under `/api/`** via `config/api_router.py` using a DRF `DefaultRouter`
  (`SimpleRouter` in production if you don't want the root browsable view).
- **Resource names are plural, kebab or snake per project, lowercase**:
  `router.register("orders", OrderViewSet)` → `/api/orders/`, `/api/orders/{id}/`.
- **Extra routes on a resource** use `@action(detail=True|False, ...)` — never a separate view:
  `@action(detail=True, methods=["post"]) def cancel(self, request, pk=None): ...` → `/api/orders/{id}/cancel/`.
- **Trailing slashes on** (DRF default). Keep it consistent.
- Non-resource endpoints (webhooks, health) live in `config/urls.py`, not the router.

## API versioning

- Version in the **URL path**: `/api/v1/...`. Mount the v1 router under `api/v1/` in `config/urls.py`
  (`path("api/v1/", include((router.urls, "v1")))`), and keep `config/api_router.py` per-version
  (`api_router_v1.py` when v2 arrives). New breaking changes → new version module; never break v1.
- Set DRF `DEFAULT_VERSIONING_CLASS = "rest_framework.versioning.URLPathVersioning"` and
  `ALLOWED_VERSIONS`. Serializers can branch on `request.version` when needed.
- drf-spectacular serves the schema at `/api/schema/`; the frontend regenerates types with
  `pnpm gen:api` after any change — keep the schema accurate.

## Nested routes

- Use **`drf-nested-routers`** for parent/child resources (`uv add drf-nested-routers`):
  ```python
  from rest_framework_nested import routers
  router = routers.DefaultRouter()
  router.register("teams", TeamViewSet, basename="team")
  teams = routers.NestedSimpleRouter(router, "teams", lookup="team")
  teams.register("members", TeamMemberViewSet, basename="team-members")
  # → /api/v1/teams/{team_pk}/members/{pk}/
  ```
- The nested ViewSet reads the parent from `self.kwargs["team_pk"]` in `get_queryset` (scope every
  query to the parent) and in `perform_create`.
- Don't nest more than **one level deep** — beyond that, use query params / filters instead.

## Permissions

- **Default is `IsAuthenticated`** (project default). A route is public only if it explicitly sets
  `permission_classes = [AllowAny]`.
- Put authorization in **permission classes**, not in views/services: object-level checks in
  `has_object_permission`, collection-level in `has_permission`. Compose small permission classes
  rather than branching inside the view.
- For ownership/tenancy, ALSO scope `get_queryset` to the request user/tenant (defense in depth —
  never rely on permissions alone to hide other users' rows).
- Admin-only actions: a dedicated permission class, not `if request.user.is_staff` in the view.

## Serializers

- Serializers own **validation and shaping**. Field-level `validate_<field>` and object-level
  `validate()` are the home for input rules. Split read vs write serializers when they diverge
  (`get_serializer_class` picks per action).
- Call a **service** from the serializer's `create`/`update` (or from `perform_create`) for anything
  beyond a trivial single-model save. Serializers must not orchestrate multi-model workflows inline.
- Type fields precisely for drf-spectacular; annotate `SerializerMethodField` with
  `@extend_schema_field`.

## Services

- `<app>/services.py`: functions/classes performing one unit of business work, wrapped in
  `@transaction.atomic`, callable from serializers, viewset actions, tasks, and management commands.
  This is where "create order → charge → email" lives.
- Services raise domain errors; the DRF exception handler maps them to responses. Services never
  touch `request`/`Response`.

## Example (the whole pattern)

```python
# core/models.py
class TimeStampedModel(models.Model):
    created = models.DateTimeField(auto_now_add=True)
    modified = models.DateTimeField(auto_now=True)
    class Meta: abstract = True

# orders/models.py
class Order(TimeStampedModel): ...

# orders/services.py
@transaction.atomic
def place_order(*, user, items) -> Order: ...

# orders/api/serializers.py
class OrderWriteSerializer(serializers.ModelSerializer):
    class Meta: model = Order; fields = [...]
    def create(self, data): return services.place_order(user=self.context["request"].user, **data)

# orders/api/views.py  — EMPTY of logic
class OrderViewSet(viewsets.ModelViewSet):
    permission_classes = [IsAuthenticated]
    def get_queryset(self): return self.request.user.orders.select_related("customer")
    def get_serializer_class(self):
        return OrderWriteSerializer if self.action in {"create","update","partial_update"} else OrderReadSerializer
```

## Testing guidelines

- **pytest + pytest-django + factory-boy**; DRF `APIClient` for endpoint tests. `pytest -n auto --reuse-db`.
- **Test the layers where the logic is**: unit-test **services** and **serializers** directly (most
  coverage here, since views are empty). Endpoint tests assert the **HTTP contract** — status codes,
  permissions (401/403 for unauth/forbidden), pagination, and response shape — not business rules.
- One **factory per model**; build test data with factories, never fixtures-by-hand.
- Cover: happy path, validation errors, permission denials (each role), and the ownership/tenancy
  scoping (user A cannot see/modify user B's rows).
- `makemigrations --check` runs in CI — never leave model changes unmigrated.

## Performance

- Always `select_related`/`prefetch_related` in the ViewSet `get_queryset` — no N+1s.
- Paginate all list endpoints; filter with `django-filter` (`filterset_fields`), never in Python.

## Health & ops

- `GET /health/` → `200 {"status":"ok"}` (no auth, no DB) for Cloud Run + local validation.
- Runs on Cloud Run as a container on `$PORT` (8080) via gunicorn — no Traefik/Nginx.
- Config via `django-environ`; secrets from env (GCP Secret Manager in prod). Never commit secrets.
